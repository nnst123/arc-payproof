# Arc PayProof 实施计划

日期：2026-09-20

依据：[已确认的设计规格](../specs/2026-09-20-arc-payproof-design.md)

## 完成定义

一个公开网页连接 Arc 主网合约，能创建一次性 USDC 发票、分享链接、完成支付并展示可核验的链上凭证。公开仓库和提交材料包含部署地址、成功演示交易、运行方式及 Arc 的实际用途。先在测试网验证，再进行主网小额演示。

## 当前环境与外部依赖

- 本地 Git 仓库只有设计规格；尚无应用代码或 Git 远端。
- Windows 上有 Node.js 24 和 npm 11；WSL Ubuntu 可运行，但尚未安装 `arc-forge`。Arc 官方的预编译 Foundry 工具面向 Linux，故合约工具放在 WSL 中使用。
- 本机没有 GitHub CLI。公开仓库与 GitHub Pages 可通过浏览器和 Git 完成，不以安装 CLI 为前提。
- 发布前需要参赛者控制的 GitHub 账号、两个演示钱包，以及少量 Arc 主网 USDC。开发与测试网阶段无需真实资金。不得索取、上传或提交私钥或助记词。

## 1. 建立项目骨架

**产物**：`contracts/`、`web/`、根目录 `README.md`、`.gitignore`。

1. 在 WSL 安装官方 Arc Foundry，并记录实际版本；用 `arc-forge init` 建立合约工程。
2. 用 Vite 建立 React + TypeScript 网页工程，安装 `viem`、`wagmi` 和必要的构建依赖。先只启用浏览器注入式钱包连接，覆盖桌面 MetaMask/Rabby 场景。
3. 固定依赖锁文件。`.gitignore` 排除 `.env`、构建产物、密钥和本地缓存；提供不含秘密的 `.env.example`。
4. 在 README 写明需求、目录、环境配置、测试网启动步骤和主网资金风险。

**验收**：合约能编译；网页能本地启动并生成生产构建；仓库无秘密文件。

## 2. 实现并验证合约

**产物**：`contracts/src/ArcPayProof.sol`、`contracts/test/ArcPayProof.t.sol`、部署脚本。

1. 定义发票结构：收款人、18 位精度金额、用途哈希、未支付/已支付状态、付款人、付款区块。ID 从 1 递增，0 永远无效。
2. 实现 `createInvoice`、`payInvoice`、`getInvoice` 以及带索引发票 ID 的创建和付款事件。创建者即收款人；支付金额必须精确匹配。支付时先更新状态，再用原生 USDC 转给收款人；收款失败则回滚。
3. 用 Arc Foundry 的本地 Arc 网络运行测试。覆盖正常创建和支付、零金额、无效 ID、错误金额、重复支付、收款失败、合约无残留付款资金，以及收款人收到精确金额。
4. 检查合约代码和部署脚本：无管理员提币入口、无升级入口、无私钥硬编码。记录编译器版本和 ABI。

**验收**：所有合约测试通过；支付交易成功后同一 ID 不可再次支付；失败交易不改变发票状态或转移本金。

## 3. 测试网部署

**产物**：测试网合约地址、部署交易哈希、部署区块高度、可复现的部署记录。

1. 从 Arc 官方文档核对测试网链 ID、RPC、浏览器和 Faucet；从 Faucet 给专用测试钱包领取测试 USDC。
2. 用 Arc Foundry 部署到 Arc Testnet。部署签名在用户控制的钱包或本地安全环境中完成；不把密钥写入仓库或输出日志。
3. 用浏览器和 RPC 分别确认合约字节码、链 ID 与部署区块。若浏览器支持源码验证，则提交合约源码验证。
4. 把网络、合约地址、部署区块写入不含秘密的 `deployments/arc-testnet.json`；前端 ABI 从编译产物生成，避免手工复制出错。

**验收**：测试网合约可读、可创建发票、可完成小额测试付款。

## 4. 实现网页流程

**产物**：创建页、发票详情页、付款状态与凭证展示。

1. 建立网络配置层：通过构建环境明确选择测试网或主网，检查链 ID 与合约地址；生产构建只指向 Arc 主网。
2. 建立表单与数据转换层：金额只接受最多两位小数并转换为 18 位链上单位；用途限制为 1–120 个 UTF-8 字节，直接哈希原始输入。
3. 创建页处理连接钱包、切换网络、提交交易、等待收据、从 `InvoiceCreated` 事件提取 ID，以及生成带查询参数的分享链接。
4. 详情页从合约读取发票，用链接说明重算哈希。优先展示链上收款地址、金额、状态；说明不匹配、发票不存在或网络错误时禁用支付。
5. 付款页调用 `payInvoice`，传入精确金额；付款后重新读链上状态。使用链上记录的付款区块和索引 ID 查询 `InvoicePaid` 事件以取得交易哈希，并链接 Arc 浏览器。
6. 用户拒签、RPC 错误、余额不足和交易回滚各显示可理解的提示。支付请求只由用户主动点击触发，不自动重发。
7. 使用 GitHub Pages 的仓库子路径配置 Vite `base`；用查询参数区分页面，确保刷新分享链接仍能打开同一发票。

**验收**：两个不同浏览器钱包可在测试网走通“创建 → 分享 → 支付 → 查看凭证”；刷新已支付发票仍能看到正确状态；更改链接说明会阻止支付。

## 5. 集成验证与发布前检查

**产物**：测试网验收记录与可发布版本。

1. 运行合约测试、网页构建，以及仅针对金额转换、说明哈希和链接解析的单元测试。
2. 手工走通两钱包测试网流程，记录创建与付款交易。检查网络切换、低余额、拒签、错误金额、重复付款和无效链接。
3. 对照 Arc 官方 EVM 差异复核原生 USDC 的 18 位精度、Gas 估算和付款回滚行为；查看合约余额与浏览器交易记录。
4. 审核公开仓库内容，确保没有私钥、助记词、真实钱包配置或不该公开的用途说明。

**验收**：测试网端到端流程通过；回归检查无失败；生产构建没有测试网合约地址。

## 6. 主网小额演示

**产物**：主网合约地址、部署区块、一个已付款的示例发票 ID 和交易哈希。

1. 再次从 Arc 官方文档及主网 RPC 核对链 ID `5042`、RPC 与 Gas 模型。
2. 估算部署、创建、付款三项费用；由参赛者给专用钱包准备小额主网 USDC。每次主网部署或付款前，展示网络、地址、金额与预计手续费，等待钱包持有人确认。
3. 部署合约，核对字节码及地址；将结果写入 `deployments/arc-mainnet.json`。
4. 用两个专用钱包创建并支付一张最小金额的公开示例发票，核对收款金额、合约余额和链上付款事件。
5. 保存可直接打开的示例发票 URL 及浏览器链接。真实资金验证失败时先诊断，不重复盲发交易。

**验收**：主网网页能读到示例发票和付款凭证；链上交易显示资金到达收款地址，合约不留存该笔付款。

## 7. 公开发布与赛事提交

**产物**：公开 GitHub 仓库、GitHub Pages 网址、README、DoraHacks 提交。

1. 将仓库推送至参赛者的 GitHub 账号，启用 GitHub Pages，并以主网合约地址生成网页。检查 HTTPS 页面与分享链接可匿名打开。
2. README 用简短英文说明问题、四步演示、合约地址、演示发票、交易链接、安装及测试命令、当前功能边界。公开源码使评审者可自行核验。
3. 在 DoraHacks 提交网页、仓库、项目用途说明和公开 GitHub 开发者主页；说明 Arc 承担真实的 USDC 结算及链上凭证。提交完成后保存提交页面或确认记录。

**验收**：不登录 GitHub 也能访问网页和仓库；评审者可从提交页一步打开已支付示例；DoraHacks 显示成功提交。
